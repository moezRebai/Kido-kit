# /kido:ask Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a new stateless `ask` pipeline stage (`/kido:ask` command, `mr-ask` skill) that answers "what does /kido:X do" and "which command fits my situation" from a table generated off the other seven stages' descriptions.

**Architecture:** `src/skills-content/ask.ts` exports `buildAskStage(otherStages: PipelineStage[]): PipelineStage`, a builder (not a plain constant like every other stage) so its body is generated from the other stages' `id`/`description` rather than hand-written — this is the one property under test. `src/pipeline/definition.ts` builds the existing 7-stage array first, then appends `buildAskStage(otherStages)`. No renderer changes: `renderClaudeCodeStage` already treats every `PipelineStage` identically.

**Tech Stack:** TypeScript (ES2022, NodeNext modules, strict), `node:test` + `node:assert/strict`, esbuild (via `build.js`) — same as the rest of the repo.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-07-27-ask-kido-design.md` — read it before starting; every task below implements a piece of it.
- Stage id is `"ask"` → skill `mr-ask`, command `.claude/commands/kido/ask.md` (per `src/pipeline/renderers/claude-code.ts`'s existing `mr-${stage.id}` / `${stage.id}.md` convention — do not hardcode these paths differently).
- `allowedTools: "Read"` only — no `Bash`/`Write`/`Edit`. The stage must never read `kido/changes/` or Jira state; that's `/kido:continue`'s job.
- No hand-written routing/decision-tree text duplicating the table — the generated table + the model's own reasoning over it covers "which command for situation X" (per spec's explicit rejection of that alternative).
- One deviation from the spec, found during planning: the spec said to add an `/kido:ask` row to `DESIGN.md`'s command table. Checking `DESIGN.md` shows `/kido:continue` — the one existing stage in the same "advisory, not a pipeline position" category as `ask` — was deliberately **excluded** from that table (see `docs/superpowers/plans/2026-07-23-kido-continue-command.md`'s "Out of scope" section). For consistency, `ask` follows the same precedent: **no `DESIGN.md` table row**. `README.md`'s quick-start list is the only doc surface both `continue` and `ask` get added to (Task 4 below).

import { test } from "node:test";
import assert from "node:assert/strict";
import { buildAskStage } from "../src/skills-content/ask.js";
import type { PipelineStage } from "../src/pipeline/definition.js";

function fakeStage(id: string, description: string): PipelineStage {
  return { id, description, allowedTools: "Read", body: `body for ${id}` };
}

test("buildAskStage sets id and allowedTools", () => {
  const stage = buildAskStage([fakeStage("document", "Builds docs.")]);
  assert.equal(stage.id, "ask");
  assert.equal(stage.allowedTools, "Read");
});

test("buildAskStage's body lists every other stage's command and description", () => {
  const otherStages = [
    fakeStage("document", "Builds docs from existing code."),
    fakeStage("specify", "Forks bug vs feature."),
  ];
  const stage = buildAskStage(otherStages);

  for (const s of otherStages) {
    assert.match(stage.body, new RegExp(`/kido:${s.id}`));
    assert.ok(stage.body.includes(s.description), `body should include ${s.id}'s description verbatim`);
  }
});

test("buildAskStage's body does not include itself", () => {
  const otherStages = [fakeStage("document", "Builds docs.")];
  const stage = buildAskStage(otherStages);
  assert.ok(!stage.body.includes("/kido:ask "), "body should not self-reference in the generated table");
});
```

import type { PipelineStage } from "../pipeline/definition.js";

export function buildAskStage(otherStages: PipelineStage[]): PipelineStage {
  const commandRows = otherStages
    .map((stage) => `| /kido:${stage.id} | ${stage.description} |`)
    .join("\n");

  const body = `You don't need to remember every /kido: command — ask.

## Commands

| Command | What it does |
|---|---|
${commandRows}

## Answering "what should I use for X?"

Match the user's situation against the table above — the descriptions already encode each command's fork points and hand-offs to the next command. Ask a clarifying question if the situation is genuinely ambiguous (e.g. bug vs. feature) rather than guessing.

## Answering "what does X do in detail?"

The table's one-liner is a summary, not the full story. Read \`.claude/commands/kido/<id>.md\` for the complete orchestration body before answering an "explain X in detail" question.

## Guardrails

- Never inspect \`kido/changes/\` or Jira state — that's \`/kido:continue\`'s job for a specific in-flight change. If the question is really "what's next for MY change" rather than "what does this command do in general," redirect there instead of guessing from this table alone.
- Don't invent behavior beyond what the table or the full command file actually says.
`;

  return {
    id: "ask",
    description:
      "Reference/router: answers \"what does /kido:X do\" and \"which command fits my situation\" from a live-generated table of every other command. Stateless — never reads kido/changes/ or Jira; redirects to /kido:continue for a specific in-flight change's status.",
    allowedTools: "Read",
    body,
  };
}
```
